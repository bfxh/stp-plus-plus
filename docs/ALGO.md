# §19 算法方向备忘：9/4 封死指数之后，还剩哪些真能减 FLOPs 的算法

> 定位：这是一份**方向备忘**，不是实施方案。读者是接手实现的工程师。
> 前提判断：ω 被钉在 9/4 之后，"靠渐近更快的矩阵乘法"这条路在理论上已经关闭。
> 剩下的算法空间只有三类：**改结构**（用更省 FLOPs 的矩阵族）、**改原语**（把乘法换成查表）、
> **改计算对象**（不是每个 token 都算全网络）。三类都不改指数，但都能改常数，其中第三类最接近"改定律"。

---

## 19.0 先把"算法突破"的边界画清楚

| 层面 | 是否还有空间 | 依据 |
|---|---|---|
| 渐近指数 ω | **没有**（≤9/4 已被下界封死） | OpenAI 2026-11-24  preprint |
| 双线性算法的常数（小尺寸秩） | **有，5–15%** | Strassen 2 层 49/64=0.766；AlphaTensor 4×4 秩 47 |
| 矩阵族（结构化） | **有，2–20× FLOPs** | Monarch `2d^{3/2}` vs 稠密 `d²`；BTT 同精度省 3.8× 算力 |
| 原语（乘→查表） | **有，2–4×** | T-MAC 无反量化、吞吐 4×；LUT 张量核 1.44× 密度 |
| 每 token 的计算量 | **有，且这是唯一能改"定律"的地方** | MoE / 动态深度 / token 选择：算力不再 ∝ token 数 |

一句话：**9/4 之后，算法突破不在"乘得更快"，在"乘得更少、或根本不用乘"。**

---

## 19.1 方向 A：为特定硬件搜索小尺寸双线性算法（AlphaTensor 路线）

**原理**：一个 n×n 乘法算法 = 矩阵乘法张量 ⟨n,n,n⟩ 的一个秩分解。Strassen 给出 2×2 用 7 次乘
（8→7，理论 12.5%）；两层 4×4 是 49 次（64→49，23%）；三层 343 次（512→343，33%）。
AlphaTensor 在 F₂ 上把 4×4 做到 **47 次**，把 (4,5,5) 做到 **76 次**（原 80），
并且**按目标硬件（V100 / TPU v2）的真实运行时搜索**，得到的算法在 wall-clock 上打赢 Strassen-square。

**为什么这条对我们可能有效**：它优化的不是 FLOPs 而是**实测运行时**（允许更多加法、换取可融合的算子），
所以能吃到编译器/张量核的形状红利。我们的形状是 n=512–2048，正好在"可用但没被优化"的区间。

**预期**：端到端 **3–10%**（不是 2×）。
**要不要 GPU 代码**：要。搜索用 Python/SAT；落地用 Triton 或 CUTLASS 写一个分块 kernel。
**第一周证伪**：n ∈ {512, 1024, 2048, 4096} 的 fp16 GEMM，用 47 次分解的 4×4 分块 vs cuBLAS；
若 n≤2048 全 <1.0 就判死（大概率如此，因为转换开销）。
**风险**：fp16 的舍入误差在非正交基下会被放大；必须报 max-abs-diff。

---

## 19.2 方向 B：把稠密线性层换成结构化矩阵族（Monarch / BTT）——**我判断最值得先做**

**原理**：Monarch 矩阵 `M = P L Pᵀ R`（两个块对角 + 置换），矩阵-向量乘 FLOPs 从 `d²` 降到 `2d^{3/2}`：
d=2048 时是 18.5 万 vs 419 万，**22× 更少**；参数量同样 `2d^{3/2}`。
论文实测：ViT / GPT-2 在 ImageNet 与 WikiText-103 上**训练快 2× 而质量相当**；
"sandwich/reverse sparsification" 让 GPT-2 预训练**2× 无掉点**，BERT 预训练比 NVIDIA MLPerf 记录还快 23%。
BTT（Block Tensor-Train，Monarch 的超集）更狠：ViT-S/32 同精度**省 3.8× 算力**，
并且论文明确声称 **"better scaling laws than dense matrices"**——这正是我们要找的东西。

**为什么它可能"改定律"**：它的 FLOPs 随宽度是 `d^{1.5}` 而不是 `d²`，模型变宽时算力增长更慢，
等价于把"参数量-算力"那条曲线掰弯。这不是把常数调小，是**换了曲线形状**。

**预期**：1B 规模、同墙钟时间下 ppl 改善 **10–30%**；同 ppl 省 **1.5–2×** 算力。
**要不要 GPU 代码**：**不要**。`torch.bmm` 的块对角乘 + 固定置换即可；纯 PyTorch。
**第一周证伪**：把 Llama-3.2-1B 的 q/k/v/o 与 gate/up/down 逐层替换为 Monarch（block 数 b=16/32），
用 Monarch 解析投影（论文给了解析最优解）初始化，再训 240 步，比 ppl；同时报实测 GEMM 时间。
**停止条件**：b=32 仍比稠密差 >5% ppl，或实测 step time 没降 → 判死。
**风险**：置换会破坏 kernel 的合并访存，实测可能只有 1.3× 而不是 2×；必须先量再扩。

---

## 19.3 方向 C：换原语——把"乘"换成"查表"（LUT / 1-bit）

**原理**：权重是低比特时，`y = W x` 不需要真的做浮点乘：把 g 个权重位分成一组，
预计算该组所有 2^g 种取值对应的激活和，运行时只做**查表 + 移位累加**。
T-MAC 在 CPU 上做到无 dequant、吞吐 **4× 于 llama.cpp**、能耗 −70%；
LUT Tensor Core 把这件事做到"计算密度 1.44×"。

**为什么是"算法"而不是"工程"**：它改变了计算的单位操作（乘法 → 索引 + 加法），
所以不受"乘法次数"这个度量的约束——这是绕开 9/4 的唯一合法方式。

**对我们的意义**：训练侧意义有限（反向仍需高精度），但**推理侧**可以把 1B 模型塞进 8GB 并跑得很快；
若目标是"单位算力能训/推多少 token"，这条值得做。
**预期**：推理 2–4×；训练 <1.2×（除非做 BitNet 式从头训练）。
**要不要 GPU 代码**：推理要（Triton 里写 gather + 累加）；训练不必。
**第一周证伪**：拿现成 T-MAC 跑我们的 1B（W4）在 CPU 上，量 tok/s 与 ppl；GPU 侧先不做。

---

## 19.4 方向 D：改"计算对象"——让每 token 的算力不再是常数（**最接近"改定律"**）

**原理**：现在的缩放定律假设 `FLOPs ∝ token 数`。一旦打破这个比例，定律的形式就变了：

- **MoE / 稀疏激活**：参数量 ↑ 但每 token 只激活一部分 → 同算力下有效容量更大（已有大量证据）；
- **动态深度 / early-exit**：简单 token 少算几层，难 token 多算；
- **token 级选择（RHO-1）**：只对"需学"的 token 回传梯度，等效于"每个 token 的信息量"不同。

**为什么这是唯一能改定律的一类**：它改的是 `L(N, D, C)` 里的**函数形式**（每个 token 的成本变成变量），
不是把某条曲线的常数调小。§17 的 L2/L4 已经在做这一类的一半（token 选择）。

**预期**：MoE 在同算力下 ppl −10–20%；early-exit 省 20–30% 算力。
**要不要 GPU 代码**：MoE 要（专家路由与 all-to-all）；early-exit 不要。
**第一周证伪**：我们的 8GB 单卡跑不动真正的 MoE，只能做"层跳过"（随机/按 loss 跳 25% 层），
看 ppl 退化是否 < 同算力稠密模型的收益。

## 19.5 优先级与判据（给接手的人）

| 顺序 | 方向 | 成本 | 我们的先验胜率 | 判据 |
|---|---|---|---|---|
| 1 | **B 结构化（Monarch/BTT）** | 3 天 | **高**（有 2× 与"更好 scaling law"的公开证据） | 同 step time 的 ppl；b 扫描 |
| 2 | **D 层跳过 / token 选择** | 2 天 | 中（§17 L2 已在路上） | 同算力 ppl，3 seed |
| 3 | C LUT 推理 | 2 天 | 中（只对推理有效） | tok/s + ppl |
| 4 | A 定制双线性算法 | 1 周 | **低**（n 太小，转换吃光收益） | n≤2048 全 <1.0 即判死 |

**统一口径**：所有结论必须写成"**等墙钟时间下的 ppl**"或"**等 ppl 下的墙钟时间**"，
不接受"理论 FLOPs 少了 22×"这类说法——Monarch 的 22× 理论值在实测里只兑现 2×，
就是因为置换与块对角让访存变碎。

## 19.6 给接手工程师的一句话

**别去碰 ω。** 先去量一次 `step time` 的构成：如果 GEMM 占比 <60%，A 和 C 都不用做；
然后把 `q/k/v/o/gate/up/down` 换成 Monarch（b=16），用解析投影初始化，训 240 步——
这一步 3 天内能给出"结构化到底能不能在我们的 1B 上兑现"的答案，比任何渐近算法都靠谱。
