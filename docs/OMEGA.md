# §18 ω=9/4 之后：底层还能做什么（给外部工程师的任务书）

> 背景：OpenAI 2026-11-24 在 `openai/math` 发布《The matrix multiplication exponent is nine fourths》，
> 声称 ω = 9/4 并给出匹配下界（⌈n^{9/4}/2⌉ 个非标量乘/除门），Lean 只覆盖无除法电路的核心指数，
> 逐尺寸界未形式化、未经同行评审。
>
> **先明确一件事：这是"不可能更快"的证明，不是"更快的方法"。** 仓库里没有 kernel，
> 达到 2.25 的构造是银河算法（常数巨大，n 要大到荒谬）。所以"底层有没有支持 2.25"的答案是：
> **没有，也不会有；任何声称"实现 2.25"的代码都是假的。**
>
> 但定理把"矩阵乘法这条路"封死了，于是真正值得投入的是三条**降低实际 FLOPs** 的路线。
> 下面每条都写清：数学、预期收益、**要不要写 CUDA**、验收标准、停止条件。

---

## 18.0 先把账算清：为什么 n=512 时 2.25 一点用都没有

理论收益 = n³ / n^{2.25} = n^{0.75}。n=4096 时是 512×，听起来惊人。但：

- 递归算法每层要付"加法/打包/布局转换"的常数；Strassen 一层是 7/8 的乘法，但要 18 次加法 + 拼接。
- 实际打平点：fp32 GEMM 在 n≈2000–4000 才可能持平；**fp16/bf16 张量核上基本不可能**，因为转换与精度损失吃掉全部收益。
- 我们的实际形状：1B 模型、seq 512、bs 4 → 每个 GEMM 的 n 在 512–2048，且是**带宽受限**（8GB / 272 GB/s）。

结论：路线 1 值得做一次"半小时的证伪实验"，不值得投入工程。

---

## 18.1 路线一：Strassen–Winograd 递归 GEMM（纯 PyTorch，不需 CUDA）

**做法**：把 A、B 各切成 2×2 块，用 7 次子块乘法（而非 8 次）组合出 C。递归 1–2 层即可；
子块乘法直接调 `torch.matmul`，让 cuBLAS 在更小的 n 上跑。

**要不要写 CUDA**：不要。全部是 Python 层的 `torch.matmul` 组合 + `torch.cat`。
**成本**：约 150 行，半天。
**预期**：fp32、n≥4096 时 1.05–1.15×；fp16 大概率 <1.0（布局转换亏）。
**验收**：`n ∈ {1024, 2048, 4096, 8192}`，fp32/fp16 各 20 次，报"TFLOPS + 相对 cuBLAS 的比值 + 数值误差（max abs diff）"。
**停止条件**：n≤2048 全部 <1.0 且 fp16 全负 → 直接判死，写进结论，不再投入。
**注意**：不要用 `torch.compile` 去融合它（会把 7 次乘法重新优化回 8 次）。

---

## 18.2 路线二：把"稠密 GEMM"换成结构化因子（TT / MPO / 低秩）——真正能改 FLOPs 的一条

**数学**：权重 `W ∈ R^{d_out × d_in}` 用张量列（TT）分解成核链，秩 χ：

- 前向 `y = W x` 的 FLOPs 从 `d²` 降到 `O(d · χ²)`；
- 参数量的压缩比在 GPT-2 规模实测 **5–13×**（χ=16 时保留 97.7% 的 token 准确率，参数量只剩 18.8%）；
- 低秩极端情形：`W ≈ B A`（r=64、d=2048）时 FLOPs 从 4.2M 降到 0.26M，**16×**。

**要不要写 CUDA**：不要（第一阶段）。TT 的前向就是若干次 `einsum`/`tensordot` + reshape，
反向交给 PyTorch autograd 即可。只有当 χ 很小、einsum 的 kernel launch 成为瓶颈时，
才值得写一个 fused contraction（那时才需要 CUDA/CUTLASS）。
**成本**：`TTLinear` 模块 + TT-SVD 初始化 + 3 组消融，约 2–3 天。
**验收**：同等**实测 FLOPs**（不是参数量）下比稠密 baseline 的 ppl：
1. 小模型（100M 级）从零预训练，TT vs 稠密，同 token 数比 ppl；
2. 1B + LoRA 场景：只替换被冻结基座的若干层为 TT（保持输出分布），比"同算力下的步数"；
3. 报"同 ppl 省多少 FLOPs"与"同 FLOPs 的 ppl 差"。
**停止条件**：χ≥64 仍打不过稠密（同 FLOPs 下 ppl 差 >3%），说明该规模下权重没有可用的低秩结构。
**风险**：TT 会破坏 LayerNorm/残差的数值尺度，必须做逐层校准（否则第一版一定崩）。

---

## 18.3 路线三：让硬件"直接兑现"的 2×2×2——2:4 结构化稀疏 + FP8

这是**唯一有厂商支持、今天就能跑出倍数的"矩阵加速"**，与 9/4 无关，但同属"底层还能榨什么"：

- **2:4 结构化稀疏**：每 4 个权重保留 2 个，张量核吞吐 ×2（cuSPARSELt，sm_80+，4060 Ti 的 sm_89 支持）。
- **FP8（E4M3/E5M2）**：Ada 第四代张量核支持，理论 ×2（消费卡的 PyTorch 路径支持不完整，需实测）。
- 两者叠加，**同带宽下最多 4×**——这比任何"更快矩阵乘法"都现实。

**要不要写 CUDA**：不必手写。用 `cuSPARSELt`（Python 绑定或 CUTLASS 的 Python 封装）
或 `torchao` 的 sparse/float8 路径；训练侧的 2:4 掩码（STE）是纯 Python。
**成本**：环境打通 + 精度曲线，约 2 天。
**验收**：(a) 同精度下 GEMM 吞吐倍数；(b) 端到端 step time 倍数；(c) ppl 退化 ≤1%；
(d) 与我们现有 4-bit bnb 路径的对比（很可能 bnb 已经把"带宽优势"吃掉了，需要诚实报告）。
**停止条件**：端到端 <1.15× 或 ppl 退化 >2% → 判死。

---

## 18.4 三条路线的共同前提：先量 MFU，否则全部是空谈

现在实测（训练并行时，被摊薄）：n=4096 只有 **16.1 TFLOPS**；单步 15.1 TFLOP、1.75 s/step
≈ **8.6 TFLOPS ≈ 峰值的 10%**。必须先回答"钱花在哪"：

1. 空载跑 `bench_mm.py`，拿真实峰值（fp16 张量，n=512/2048/4096）；
2. 用 `torch.profiler` 拆一次 step：GEMM / 反量化 / LayerNorm / optimizer / 数据加载 各占多少；
3. 结论只允许两种：**算力受限**（那就走路线一/三）或**带宽受限**（那三条都别做，换卡或减 token）。

**判据**：若 GEMM 时间占比 <60%，则任何"更快矩阵乘法"的收益上界就是那 60%，
路线一可以直接不做。

## 18.6 一句话总结给外部工程师

**别去实现 2.25，那不存在。** 先把 MFU 量出来：若算力受限，走 Strassen（便宜、大概率无效）
或 2:4+FP8（现实、但要过精度关）；若带宽受限，唯一有效的是路线二（结构化因子）
——因为它减少的是**要搬的字节和要算的 FLOPs**，而不是"每 FLOP 更快"。
