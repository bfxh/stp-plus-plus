# §20 GPU 层：9/4 这条定理到底对 GPU 有什么作用

> 直答：**对 GPU 的作用是零，而且是"成本模型错配"造成的零，不是"还没实现"的零。**
> 下面把这件事在 GPU 层拆开，顺便给出我们这张卡的真实瓶颈在哪。

---

## 20.1 定理数的是"门"，GPU 数的是"指令 + 字节"

| 维度 | 9/4 定理的模型 | GPU 的真实模型 |
|---|---|---|
| 计量单位 | 非标量乘/除门的个数 | FMA 指令（乘加融合成一条） |
| 加法 | **免费**（可任意增加） | 要额外指令、要占用发射槽 |
| 数据搬运 | **免费**（无内存层级） | 288 GB/s、L2 32 MB、每次 tile 都要 load/store |
| 规模 | 渐近（n→∞） | n=512–2048，纯常数区 |
| 结论形态 | 下界（不可能更快） | 只关心"这个 kernel 在 34 个 SM 上跑满没有" |

关键点：GPU 里**乘法从来不是一条独立指令**，是 FMA 的一半；所以"省一次乘法"在硬件上不省任何周期，
而 Strassen 类算法为此付出的加法、拼接、布局转换却全是真金白银的指令和字节。
**定理在它的模型里成立，在 GPU 的模型里连"可兑换"都谈不上。**

## 20.2 它唯一"碰到"GPU 的地方，是给硬件路线判了个死刑

既然 ω 的下界是 2.25，且实际算法都在 2.37 以上、常数巨大，那么：

> GPU 厂商不能指望"某个更快的矩阵乘法算法"带来免费算力；
> 只能靠 **更多 MAC、更大缓存/带宽、更低精度、结构化稀疏** 这四件事。

这对我们是**反面教材**，不是方法论：别在算法层找 GPU 收益，收益只在这四个旋钮里。

## 20.3 我们这张卡的真实数字（RTX 4060 Ti，sm_89，34 SM）

- 显存：8 GB，128-bit，9.0 GHz DDR → **288 GB/s**；L2 **32 MB**
- FP16 张量峰值：约 **88 TFLOPS**（4×FP32 折算，需空载实测确认）
- 实测（训练并行时被摊薄）：n=4096 仅 **16.1 TFLOPS**；单步 15.1 TFLOP / 1.75 s ≈ **8.6 TFLOPS ≈ 10% MFU**
- Roofline 拐点：88 TFLOPS / 288 GB/s ≈ **306 FLOP/byte**
- 我们这一步的算术强度：15.1 TFLOP / ~1.5 GB ≈ **10⁴ FLOP/byte**，比拐点高一个量级

**结论：不是带宽打满，是张量管空闲。** 也就是说，问题在"kernel 没把 SM 喂满"，
不在"矩阵乘法算法不够快"——这正好又说明 9/4 帮不上忙。

三个待验证的假设（按可能性排序）：

1. **bnb 4-bit 反量化**：每层 GEMM 前都要 dequant，反量化 kernel 是纯带宽操作，把张量管打断；
2. **M 太小**：bs=4、seq=512 → 单次 GEMM 的 M=2048 看着不小，但 LoRA 的 r=16 让部分 GEMM 退化成 skinny；
3. **Python/调度开销**：每步多次 kernel launch + eval 插入，1.75 s 里可能有 0.3–0.5 s 是空转。

## 20.4 GPU 层该做什么（给接手的人，30 分钟能跑完）

用 Nsight Compute 抓 20 个 step，只看 6 个指标：

| 指标 | 看什么 | 判据 |
|---|---|---|
| `sm__pipe_tensor_op_hmma_cycles_active` | 张量管占用率 | <30% → 张量管空闲，先修 kernel |
| `dram__bytes.sum.per_second` | 实际带宽 | 接近 288 GB/s → 带宽墙 |
| `l1tex__throughput` | L1/共享内存压力 | 高 → tile 太小、访存碎 |
| `smsp__warp_issue_stalled_*` | warp 在等什么 | 等内存 / 等 barrier / 等指令 |
| `sm__throughput` | SM 整体占用 | 与张量管对比，定位非 GEMM 开销 |
| `launch__occupancy_limit_*` | 占用率被谁限制 | 寄存器 / 共享内存 / block 数 |

**动作顺序**：先确认"GEMM 占 step 时间的比例"（若 <60%，任何矩阵加速的上界就是那 60%），
再决定是换精度（FP16→FP8，Ada 有指令支持但 PyTorch 路径不完整，需实测）、
上 2:4 稀疏（cuSPARSELt，sm_89 支持），还是干脆把 bnb 换掉（用 fp16 基座 + LoRA，牺牲显存换吞吐）。

## 20.5 一句话总结

**9/4 是纸上的下界，GPU 只认 FMA、字节和占用率。**
它对我们唯一的用处是：证明"在算法层等一个更快的矩阵乘法"这件事永远等不到，
于是把精力全部押到"更少的 token / 更少的字节 / 更低的精度"——这三件事才是 GPU 层能兑现的。
