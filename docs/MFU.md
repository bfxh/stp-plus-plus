# §24 MFU 实测：这张卡能跑多快，以及为什么"少做乘法"救不了它

> 全部数据来自本机实测（WSL2 + nvcc 13.0 + cuBLAS，`sm_89`，RTX 4060 Ti 8GB）。
> 测量期间后台预训练 sweep 一直在占卡，所以**绝对值受时间片污染**；凡是跨实现的比较都在同一进程内背靠背测，只信比值。

## 24.1 可达算力：48.5 TFLOPS，不是 88

`kernels/mfu_probe.cu`，best-of-30，扫真实 1B 模型的四种 GEMM 家族：

| 形状 (M,N,K) | 用途 | cuBLAS 最好 |
|---|---|---|
| (1024, 8192, 2048) | gate/up | 41.1 TFLOPS |
| (2048, 8192, 2048) | gate/up | 47.4 |
| (8096, 4096, 8192) | mlp wide | 48.5 |
| (4096, 8192, 2048) | gate/up | 48.2 |
| (1024, 32000, 2048) | lm_head | 48.4 |

**峰值 ≈ 48.5 TFLOPS（fp16 输入 / fp32 累加）**，也就是标称 88 的 55%。M 从 1024 涨到 8192，效率从 44% 只涨到 55%——**M 不是主因**，cuBLAS 在这张消费卡上就是这个水平。

## 24.2 精度模式：fp16 累加是 1.8×，但 PyTorch 拿不到

`kernels/prec_probe.cu`，同形状背靠背：

| 模式 | 相对 |
|---|---|
| fp16 输入 + **fp32 累加** | 1.00× |
| fp16 输入 + **fp16 累加**（`CUBLAS_COMPUTE_16F`） | **1.80×**（1.65–1.92，四个形状一致） |
| bf16 输入 + fp32 累加 | 0.99×（≈ fp16/acc32） |
| FP8 E4M3（`CUDA_R_8F_E4M3`） | **UNSUPPORTED**（cublasGemmEx 直接返回错误，这张卡没有可用路径） |

**关键**：这 1.8× 只在 `cublasGemmEx` 显式传 `CUBLAS_COMPUTE_16F` 时出现。
把训练器切到 `--no-bf16 --fp16` 并打开 `allow_fp16_reduced_precision_reduction` 后，20 步 **27.3 s**，和 bf16 调优后的 27.5 s 一样——**PyTorch 的 autocast 不会降低累加精度**，那个开关只影响 split-K 的归约。要拿这 1.8× 必须自己包一层 autograd Function 调 cuBLAS。

## 24.3 训练步到底花在哪（kernel 级）

`STPP_PROFILE=1` + `scripts/prof_summary.py`，抓 3 个完整 step：

| 类别 | ms/step | 占比 | 调用数/step |
|---|---|---|---|
| GEMM（bf16 + fp32） | 500.5 | 47.8% | 544 |
| **elementwise** | **429.0** | **41.0%** | **3813** |
| softmax | 70.3 | 6.7% | 56 |
| dropout | 41.8 | 4.0% | 224 |
| reduce/norm | 4.8 | 0.5% | 32 |

单看 GEMM：15.1 TFLOP/step ÷ 0.50 s ≈ **30 TFLOPS**，是可达值的 62%。**GEMM 并不烂**。
烂的是：**每步 3813 次 elementwise launch**，平均每次只干 0.11 ms 的活，把 41% 的 GPU 时间烧在搬 bf16 张量上。

## 24.4 能立刻拿到的（A/B 实测，20 步背靠背）

| 臂 | 配置 | 20 步 | 相对 |
|---|---|---|---|
| A | 默认（chunk=64, dropout=0.05） | 30.2 s | 1.00× |
| A2 | 同上，复测 | 29.4 s | 1.03× |
| B | `STPP_LOGIT_CHUNK=512` | 28.5 s | **−5.6%** |
| C | B + `--lora_dropout 0.0` | **27.5 s** | **−8.4%** |
| D | C + `--no-bf16 --fp16` + scaler | 27.3 s | −8.6%（无额外收益，且有数值风险） |

两个能稳拿的：**lm_head 分块从 8 段并成 1 段**（`STPP_LOGIT_CHUNK=512`），**LoRA dropout 归零**。

## 24.5 试过但在这台机器上不成立的三条

1. **`torch.compile`**：`InductorError: TritonMissing` —— 原生 Windows 上 Triton 装不上，inductor 无法融合那 3813 次 elementwise。**这是 41% 那部分唯一便宜的解法，但它在这台机器上是死的。** 要它就得迁到 WSL/Linux 重装整套 torch 环境。
2. **`bs 4 → 8`**（想让 GEMM 的 M 翻倍）：**4090 ms/step，每序列 511 ms**，而 bs=4 是 345 ms/序列 —— **慢 48%**。8GB + WDDM 直接换页。bs=4 已经是这张卡的最优点，往上只有负收益。
3. **FP8 / 2:4 稀疏**：FP8 在 cublasGemmEx 上 unsupported；2:4 稀疏需要 `mma.sp` 自写 tile，属于下一节的内核工作。

## 24.6 把三件事串起来看（这才是"能不能突破缩放定律"的答案）

| 路线 | 理论上限 | 本机实测 | 结论 |
|---|---|---|---|
| ω=9/4 / Strassen 一层 | 8/7 = **1.14×** | **0.93×**（3-launch 融合） | 尺寸差 4–8 倍，带宽差 3.8 倍 → 不可兑现 |
| 训练器调参（chunk / dropout） | ~1.1× | **1.08×**（1.49→1.38 s/step） | 已落地 |
| **fp16 累加（16F）** | **1.8×**（GEMM）→ 步级 ~1.3× | cuBLAS 层已验证，PyTorch 层拿不到 | **必须包自定义 GEMM** |
| **elementwise 融合** | 41% → 10%，步级 **~1.5×** | 被 Triton 缺失堵死 | **必须写内核或迁 Linux** |
| 两者叠加 | — | 估算 **1.9–2.2×** | 唯一能到 2× 的组合 |

所以"把训练效率拉到最大"在本机的真实路径只有一条：**写内核**。具体是三个可交付物：

- **K-A 融合逐元素内核**：把 residual add + dropout + mask + CE gather 合到 1–2 个 kernel，目标把 3813 次/步降到 <800 次。验收：步时间 ≤0.8×。
- **K-B 16F 累加 GEMM 封装**：`autograd.Function` → `cublasGemmEx(CUBLAS_COMPUTE_16F)`，配 per-tile 的 scale 防溢出。验收：GEMM 段 −40%，20 步无损。
- **K-C（已否）** Strassen/ω：上限 1.14×，实测 0.93×，不做。

**这才是"2.25 用不到全盘"的真正替代品：不是少做 12.5% 的乘法，而是把 41% 的搬运时间和 1.8× 的累加路径拿回来。**
