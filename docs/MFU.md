# §24 MFU 实测：这张卡能跑多快，以及为什么"少做乘法"救不了它

> 全部数据来自本机实测（WSL2 + nvcc 13.0 + cuBLAS，`sm_89`，RTX 4060 Ti 8GB）。
> 测量期间后台预训练 sweep 一直在占卡，所以**绝对值受时间片污染**；凡是跨实现的比较都在同一进程内背靠背测，只信比值。

## 24.1 可达算力：48.5 TFLOPS，不是 88

`kernels/mfu_probe.cu`，best-of-30，扫真实 1B 模型的四种 GEMM 家族：

| 形状 (M,N,K) | 用途 | cuBLAS 最好 |
|---|---|---|
| (1024, 8192, 2048) | gate/up | 41.1 TFLOPS |
| (2048, 8192, 2048) | gate/up | 47.4 |
| (8096, 4096, 8192) | mlp wide | 48.5 |
| (4096, 8192, 2048) | gate/up | 48.2 |
| (1024, 32000, 2048) | lm_head | 48.4 |

**峰值 ≈ 48.5 TFLOPS（fp16 输入 / fp32 累加）**，也就是标称 88 的 55%。M 从 1024 涨到 8192，效率从 44% 只涨到 55%——**M 不是主因**，cuBLAS 在这张消费卡上就是这个水平。

## 24.2 精度模式：fp16 累加是 1.8×，但 PyTorch 拿不到

`kernels/prec_probe.cu`，同形状背靠背：

| 模式 | 相对 |
|---|---|
| fp16 输入 + **fp32 累加** | 1.00× |
| fp16 输入 + **fp16 累加**（`CUBLAS_COMPUTE_16F`） | **1.80×**（1.65–1.92，四个形状一致） |
| bf16 输入 + fp32 累加 | 0.99×（≈ fp16/acc32） |
| FP8 E4M3（`CUDA_R_8F_E4M3`） | **UNSUPPORTED**（cublasGemmEx 直接返回错误，这张卡没有可用路径） |

**关键**：这 1.8× 只在 `cublasGemmEx` 显式传 `CUBLAS_COMPUTE_16F` 时出现。
把训练器切到 `--no-bf16 --fp16` 并打开 `allow_fp16_reduced_precision_reduction` 后，20 步 **27.3 s**，和 bf16 调优后的 27.5 s 一样——**PyTorch 的 autocast 不会降低累加精度**，那个开关只影响 split-K 的归约。要拿这 1.8× 必须自己包一层 autograd Function 调 cuBLAS。

## 24.3 训练步到底花在哪（kernel 级）

`STPP_PROFILE=1` + `scripts/prof_summary.py`，抓 3 个完整 step：

| 类别 | ms/step | 占比 | 调用数/step |
|---|---|---|---|
| GEMM（bf16 + fp32） | 500.5 | 47.8% | 544 |
| **elementwise** | **429.0** | **41.0%** | **3813** |
| softmax | 70.3 | 6.7% | 56 |
| dropout | 41.8 | 4.0% | 224 |
| reduce/norm | 4.8 | 0.5% | 32 |

单看 GEMM：15.1 TFLOP/step ÷ 0.50 s ≈ **30 TFLOPS**，是可达值的 62%。**GEMM 并不烂**。
烂的是：**每步 3813 次 elementwise launch**，平均每次只干 0.11 ms 的活，把 41% 的 GPU 时间烧在搬 bf16 张量上。

## 24.4 能立刻拿到的（A/B 实测，20 步背靠背）

| 臂 | 配置 | 20 步 | 相对 |
|---|---|---|---|
| A | 默认（chunk=64, dropout=0.05） | 30.2 s | 1.00× |
| A2 | 同上，复测 | 29.4 s | 1.03× |
| B | `STPP_LOGIT_CHUNK=512` | 28.5 s | **−5.6%** |
| C | B + `--lora_dropout 0.0` | **27.5 s** | **−8.4%** |
| D | C + `--no-bf16 --fp16` + scaler | 27.3 s | −8.6%（无额外收益，且有数值风险） |

两个能稳拿的：**lm_head 分块从 8 段并成 1 段**（`STPP_LOGIT_CHUNK=512`），**LoRA dropout 归零**。

## 24.5 试过但在这台机器上不成立的三条

1. **`torch.compile`**：`InductorError: TritonMissing` —— 原生 Windows 上 Triton 装不上，inductor 无法融合那 3813 次 elementwise。**这是 41% 那部分唯一便宜的解法，但它在这台机器上是死的。** 要它就得迁到 WSL/Linux 重装整套 torch 环境。
2. **`bs 4 → 8`**（想让 GEMM 的 M 翻倍）：**4090 ms/step，每序列 511 ms**，而 bs=4 是 345 ms/序列 —— **慢 48%**。8GB + WDDM 直接换页。bs=4 已经是这张卡的最优点，往上只有负收益。
3. **FP8 / 2:4 稀疏**：FP8 在 cublasGemmEx 上 unsupported；2:4 稀疏需要 `mma.sp` 自写 tile，属于下一节的内核工作。

## 24.6 把三件事串起来看（这才是"能不能突破缩放定律"的答案）

| 路线 | 理论上限 | 本机实测 | 结论 |
|---|---|---|---|
| ω=9/4 / Strassen 一层 | 8/7 = **1.14×** | **0.93×**（3-launch 融合） | 尺寸差 4–8 倍，带宽差 3.8 倍 → 不可兑现 |
| 训练器调参（chunk / dropout） | ~1.1× | **1.08×**（1.49→1.38 s/step） | 已落地 |
| **fp16 累加（16F）** | **1.8×**（GEMM）→ 步级 ~1.3× | cuBLAS 层已验证，PyTorch 层拿不到 | **必须包自定义 GEMM** |
| **elementwise 融合** | 41% → 10%，步级 **~1.5×** | 被 Triton 缺失堵死 | **必须写内核或迁 Linux** |
| 两者叠加 | — | 估算 **1.9–2.2×** | 唯一能到 2× 的组合 |

所以"把训练效率拉到最大"在本机的真实路径只有一条：**写内核**。具体是三个可交付物：

- **K-A 融合逐元素内核**：把 residual add + dropout + mask + CE gather 合到 1–2 个 kernel，目标把 3813 次/步降到 <800 次。验收：步时间 ≤0.8×。
- **K-B 16F 累加 GEMM 封装**：已验证可行（见 24.8），**但在 8GB 上装不进训练器**——需要 ≥12GB 显存余量或零拷贝的 C++ 扩展才成立。
- **K-C（已否）** Strassen/ω：上限 1.14×，实测 0.93×，不做。

**这才是"2.25 用不到全盘"的真正替代品：不是少做 12.5% 的乘法，而是把 41% 的搬运时间和 1.8× 的累加路径拿回来。**

## 24.7 训练线（同一批实验）现状

| 步数 | seed 82 / 23 / 37 | 均值 |
|---|---|---|
| 240 | 6.397 / 6.356 / 6.387 | **6.380** |
| 480 | 6.171 / 6.133 / 6.169 | **6.158**（−3.5%） |
| 960 | 原 Windows run 在 00:26 被会话中断杀掉；改用 Linux+compile（0.53 s/步）重跑 | — |

240→480 的 ppl 降幅是 3.5%。若按同一幂律外推，960 应落在 **≈5.94**；这条曲线是后面 L2（超额损失 token 选择）唯一的对照基线。

## 24.8 16F 累加：单测 1.8× 成立，装进训练器反亏

`stpp/gemm16.py` —— 不编译扩展，用 ctypes 直连 torch 自带的 `cublas64_12.dll`，`autograd.Function` 里调 `cublasGemmEx(CUBLAS_COMPUTE_16F)`。
两个关键坑：① `COMPUTE_16F` 下 alpha/beta 必须是 **2 字节的 `__half` 本体**，传 float 会被读成 0（结果全零但不报错）；② 列主序必须是 `op(A)=T` 对 `(N,K)` 权重的那个形式。

数值（`kernels/acc16_check.cu`，K=2048/8192，act~N(0,1)、w~N(0,0.02)，对 CPU float64 参考）：

| 形状 | fp32-acc 误差 | fp16-acc 误差 | 非有限 |
|---|---|---|---|
| (2048,8192,2048) | 0.06% of rms | **0.59%** | 0 |
| (2048,2048,8192) | 0.09% | **0.69%** | 0 |
| (2048,32000,2048) | 0.07% | **0.73%** | 0 |

和 bf16 自身的输入舍入（2⁻⁸ ≈ 0.4%）同量级 —— **数值上完全可用，这是这张卡上唯一"白捡 1.8×"的地方**。

单独测（`scripts/test_gemm16.py`，best-of-30，同进程背靠背）：

| 形状 | torch (32F 累加) | gemm16 (16F 累加) | 倍数 | 误差%rms |
|---|---|---|---|---|
| (2048,8192,2048) | 1.611 ms | 0.891 ms | **1.81×** | 3.24 |
| (2048,2048,8192) | 1.530 | 0.898 | **1.70×** | 2.48 |
| (2048,32000,2048) | 5.642 | 3.402 | **1.66×** | 3.89 |

反传也对（dx/dw 相对 fp32-累加路径的最大差 2.7e-3 / 1.7e-3）。

**但装进训练器是净亏**：`--fp16 --no-bf16` 加 `STPP_GEMM16=1`，20 步 **44.1 s**，而不加是 27.3 s。
原因不是 kernel，是**显存**：wrapper 要给每个 GEMM 存 `a`/`b`、反传要 `g.t().contiguous()` 造 33MB 级的拷贝，16 层×7 投影×3 次（前向+重算+反向）≈ 每步多出 GB 级临时张量，8GB 直接换页 —— 和 24.5 里 `bs=8` 是同一种死法。

结论：**K-B 需要 ≥12GB 余量，或一个零拷贝的 C++ 扩展（Windows 侧缺 MSVC，只能在 WSL/Linux 里做）**。在这台 8GB 机器上，它只能停在"单测 1.8×"。

## 24.9 换到 Linux：1.44×；再加 torch.compile：2.61×

Windows 上 `torch.compile` 直接死（`TritonMissing`）。WSL2 Ubuntu-24.04 里装 torch 2.11.0+cu128（自带 Triton 3.6），同一份代码、同一张卡，跑出来了：

| 环境 | bs | 每步 | 相对 Windows |
|---|---|---|---|
| Windows 11 + WDDM | 4 | **1.37 s** | 1.00× |
| WSL2 Linux | 4 | **0.95 s** | **1.44×** |
| **WSL2 + `torch.compile`(default)** | 4 | **0.525 s** | **2.61×** |
| WSL2 + `reduce-overhead`(CUDA graphs) | 4 | 0.64 s | 2.14× |
| WSL2 Linux, bs=8 | 8 | 3.33 s（417 ms/序列） | 0.57×/token |

三点读法：
- **Linux 本身就快 1.44×**：没有 WDDM 的时间片和显存预留，同一个 step 直接省 30%。
- **`torch.compile` 再把 1.81× 叠上去**，正好落在 24.3 里 elementwise 那 41% 上（3813 次/步被融合）。编译是一次性成本 ≈60 s。
- **`reduce-overhead` 反而更慢**（0.64 > 0.525）：CUDA graphs 在梯度检查点 + 动态 loss 上不划算，用默认模式。
- **bs=8 在 Linux 上也救不回来**（417 vs 237 ms/序列）：8GB 是硬墙，不是调度问题。

数值一致性核过：Windows `2.3322/2.1563/1.9007/2.3759`，Linux 编译后 `2.3310/…/2.0472/2.8434` —— **只差小数点后第三位**，是融合 kernel 的舍入差，不是数学变了。

## 24.10 今天真正能拿到的倍数

| 手段 | 倍数 | 状态 |
|---|---|---|
| Windows 基线 | 1.00× | — |
| chunk 512 + dropout 0 | 1.08× | 已落地 |
| 迁到 Linux | 1.44× | 已验证 |
| **+ torch.compile** | **2.61×** | **已验证，loss 一致** |
| 16F 累加 GEMM（K-B） | 再 ×1.3（估算） | 单测 1.8×，8GB 装不进 |
| Strassen / ω=9/4 | 1.00×（上限 1.14×，实测 0.93×） | 已否 |

**这就是"把训练效率拉到最大"的当前答案：2.61×，白拿，不需要写一个新算法。** 而 ω=2.25 那条线在这张卡上贡献 0。
剩下的空间（16F 累加）卡在 8GB 显存上，不是卡在数学上。


## §24.11 收尾：960 曲线 / 零拷贝扩展 / 编译后新瓶颈 / 8GB 硬墙

### (a) L0 曲线补到 960 步（三 seed，Linux + compile）
| 步数 | 三个 seed | 均值 | 相对上一档 |
|---|---|---|---|
| 240 | 6.397 / 6.356 / 6.387 | 6.380 | — |
| 480 | 6.171 / 6.133 / 6.169 | 6.158 | **−3.5%** |
| 960 | 5.9889 / 5.9773 / 6.0017 | **5.989** | **−2.7%** |

每翻一倍步数的收益在收窄（3.5% → 2.7%），说明正在逼近这条曲线的底。`runs/curve960/results.json`。
（原 Windows 侧 960 run 在 00:26 被会话中断杀掉，这份是 Linux+compile 重跑的，也是唯一留存的一份。）

### (b) 零拷贝 C++ 扩展：单算子 1.8×，端到端 0×
`csrc/gemm16.cpp` + `stpp/gemm16_ext.py`，三个入口 `nt/dx/dw`，转置全部折进 cuBLAS 的 op flag，反传零拷贝、无 device code（g++ 编译，绕开 nvcc 版本问题）。

| 项目 | 数字 |
|---|---|
| 前向 2048³ | **1.82×**（1.67–1.85×） |
| 前向+反传 | **1.31×** |
| 数值误差 | 2.5–3.9% of rms；反传 rel 1.7e-3 ~ 2.7e-3 |
| 进训练器（Linux+compile+fp16+ext） | **0.64 s/步** |
| 同栈无扩展（Linux+compile+fp16） | **0.583 s/步** |

结论：**净亏**。原因不是扩展写得不好，是两件事：(1) 编译后 GEMM 已占 83%，1.8× 只作用在 GEMM 那一段，Amdahl 上限有限；(2) 自定义 autograd Function 会打断 Dynamo 的图，把原本被 fuse 掉的逐元素又漏回来。

### (c) 编译后瓶颈搬家：逐元素 41% → 3.5%
`STPP_COMPILE=1` + `STPP_PROFILE=1`（3 步窗口）：

| 类别 | ms/步 | 占比 | calls/步 |
|---|---|---|---|
| **GEMM** | **406.2** | **83.2%** | 1124 |
| other | 33.6 | 6.9% | 31 |
| copy/fill | 18.5 | 3.8% | 77 |
| elementwise | 17.3 | 3.5% | 11 |
| softmax | 12.6 | 2.6% | 2 |

逐元素从 429 ms（41%）掉到 17.3 ms（3.5%）——Inductor 把所有 pointwise 全 fuse 了，3813 次 launch 消失。**瓶颈彻底换到 GEMM。**
但 GEMM 只有 ~26 TFLOPS（13 TFLOP/步 ÷ 0.488 s），= 隔离可达 48.5 的 **55%**。顶部两个 kernel 是 `128x128_ldg8` 小 tile（192 次 / 112 次调用），说明 LoRA r16 的七个小投影把 GEMM 切碎了，tile 上不去。

### (d) 8GB 硬墙在 Linux 也成立
| 配置 | s/步 | 每 token |
|---|---|---|
| bs4 + compile | 0.525 | 基准 |
| bs8 + compile | **2.43** | 差 **2.3×** |

bs=8 不是"慢一点"，是直接塌掉（换页）。这条卡上 bs 只能 4。

### (e) 最终成绩表（更新 §24.10）
| 手段 | s/步 | 倍数 | 状态 |
|---|---|---|---|
| Windows 基线 | 1.37 | 1.00× | — |
| chunk512 + dropout0 | 1.265 | 1.08× | 已落地 |
| 迁 Linux | 0.95 | 1.44× | 已验证 |
| **+ torch.compile** | **0.525** | **2.61×** | **当前冠军，loss 一致** |
| + 16F 零拷贝扩展 | 0.64 | 0.82× | 实测为负 |
| + bs8 | 2.43 | 0.22× | 实测为负 |
| + reduce-overhead(CUDA graphs) | 0.64 | 0.82× | 实测为负 |

**结论：这台 8GB 4060 Ti 上，"训练效率拉到最大"的答案是 2.61×，而且是白拿的（不用写新算法、不用改数学）。剩下的空间不在数学上，在显存和 GEMM 切碎上。**

### (f) 如果继续，优先级
1. **P1 融投影**（q/k/v → 一个 GEMM，gate/up → 一个 GEMM）：把 1124 次调用压到 ~700，让 cuBLAS 选 256×128 tile。纯模块层、不改数学，预计 10–20%。
2. **P2 换卡**（24GB）：bs 16 与 16F 累加可以同时成立，2.61× 之上再叠 1.3–1.8×。
3. **P3 ω=2.25**：已闭（§23），与本卡无关。
