## 25.3 为什么论文倍数不能直接搬过来（三条硬约束）

1. **只训 11.3M 参数**。Muon 的正交化作用在 LoRA 的 A/B 因子上，不是全权重矩阵；论文里的 2× 是全参预训练。二阶几何在低秩子空间里是否还成立，没人测过。
2. **1B + 短程**。AdEMAMix 的收益来自"几十万步之前"的梯度（β3=0.9999），我们 1920 步的总长度只有它记忆窗口的 1/5；Muon 的 2× 也是 compute-optimal（~20 token/参数）下的，我们是 11.8M/1B ≈ 0.012 token/参数，处在完全不同的区间。
3. **判定阈值**。旧集三 seed 极差 0.013 → 只有 **ppl 差 > 0.02** 才算真信号；单 seed 的 0.01 级差异一律当噪声。

### fp16/16F 为什么这次成了（唯一一个真赢的）

早期那次 `--fp16` A/B 是在**编译前**做的：当时 elementwise 429 ms / 41%，GEMM 500 ms / 47.8%，瓶颈是 3813 次逐元素 launch；dtype 换 16F 只作用于不到一半的墙钟，还被自定义 Function 打断的图吃掉收益。编译后局面翻转——elementwise 被 fuse 到 17.3 ms（3.5%），GEMM 变成 406 ms / 83.2%，16F 累加直接压在 83% 的骨架上。

关键在**不用自定义 Function**：整模型换 fp16 权重 + GradScaler，PyTorch 自己就向 cuBLAS 发 16F 累加，inductor 图完整、无 graph break。所以：

| | bf16（基线） | fp16/16F | 变化 |
|---|---|---|---|
| ppl | 4.004 | 4.004 | 0（CE 都是 1.387） |
| 墙钟 1920 步 | 1262 s | **1051 s** | **−16.7%（1.20×）** |
| 步时间 | 0.657 s | 0.547 s | — |

loss 逐位一致说明这 20% 不是拿精度换的。为什么只有 1.20× 而不是探针的 1.65–1.92×：还有一部分 GEMM 没走到 16F（大概率是 lm_head 与 attention 里的 fp32 路径）。下一步用 `STPP_PROFILE=1` 剖一版 fp16 的 320 步就能定位。

### Muon 为什么输（第一版结论）

1. **作用对象不对**。论文里的 2× 是对**全权重矩阵**做正交化；我们只训 LoRA 的 A/B 因子（16×2048 与 2048×16）。把低秩因子的动量正交化，等于把"该往哪个低秩方向走"的信息抹平成满秩方向——这恰好破坏了 LoRA 赖以生效的低秩结构。
2. **更新谱被强行拉平**。NS 把奇异值全部推到 1，等于对所有方向等权；而 LoRA 训练早期真正需要的是少数几个大奇异值方向。
3. **还更慢**。7 组 LoRA × 2 个矩阵 × 5 次 NS 迭代，虽然每个矩阵只有 16×2048，但 launch 数上去了，+15% 墙钟。

结论：**Muon 不是这套 LoRA 配置的解**。它在全参预训练上的 52% FLOPs 不能迁移到"只训 0.9% 参数"的场景。这条要写进负面结果，避免下次再试。

### AdEMAMix 为什么只是平局

1. **记忆窗口对不上长度**。β3=0.9999 的等效窗口约 1/(1−β3)=10,000 步；我们总共只跑 1,920 步，慢 EMA 只覆盖窗口的 19%，退化成"全历史平均梯度"。论文那 +95% 的 token 效率来自 101B token / 78 token·参数 的长程训练，我们是 0.012 token/参数。
2. **三个 state buffer 是纯开销**。m1/m2/v 三份状态 + 额外 elementwise，步时间 0.786 s（+20%），质量只在噪声内改善 0.007 —— 用 20% 算力换 0.2% ppl。
3. **同 Muon 的结论**：1B + LoRA + 短程，优化器层面的论文收益搬不过来。ICLR 2026 在 1.2B 全参上测到的也只是 ≈1.1×；我们在"只训 0.9% 参数"下连 1.1× 都没拿到。

**优化器这条线到此为止**（AdamW 保持不变），除非换全参训练。

## 25.7 容量：唯一一条还在单调下降、且不花墙钟的轴

都在 8.85M 语料、1920 步、seed 82、bs4、compile 上：

| rank | 可训参数 | ppl | Δ vs r16 | 墙钟 |
|---|---|---|---|---|
| 16（基线） | 11.3M | 4.004 | — | 1262 s |
| 32 | 22.5M | 3.958 | **−0.046** | 1239 s |
| 64 | 45.1M | 3.931 | **−0.073** | 1265 s |

两件事同时成立：

1. **单调、超出噪声**。−0.046 和 −0.073 都远大于 0.013 的 seed 极差；r64 相对 r32 还再降 0.027，说明没饱和。
2. **墙钟几乎不变**。r16→r64 参数 ×4，步时间 0.657→0.659 s（+0.3%）。LoRA 的额外 FLOPs 是 `2·r·d` 量级，相对 `d²` 的骨干可以忽略；显存也只多了 34M 参数 × 2 bytes ≈ 68 MB。

换算成"token 等价"：用 §7.1 的拟合 `3.8006 + 2.898e5·N^-0.9351`，3.931 对应 N≈6.1M token；而 r64 本步只用了 3.93M token（1920 步 × 2048）。**也就是说 rank 16→64 相当于白送 1.55× 的数据，一秒都不用多花。**

这是这轮唯一一个"同墙钟换更低 loss"的杠杆，而且和数据轴、优化器轴都不一样——它改的是**每 token 能被吸收多少**，不是"给多少 token"或"怎么走梯度"。

**转折在 r128**：ppl 3.948，不但比 r64 差 0.017，步时间还涨到 0.878 s（+34%）。两头都亏，说明 **r64 就是这套设置的最优点**，不是"越大越好"：

- 容量侧：r16→r64 是 11.3M→45.1M（4×），ppl −0.073；r64→r128 是 45.1M→90.2M（2×），ppl 反而 +0.017。1920 步 / 3.93M token（0.44 epoch）能喂饱的参数就这么多，再大就是过参数化。
- 成本侧：LoRA 的额外 matmul 是 `2·r·d` 每层，r=128 时已到 `d²` 的 12%，加上 Adam 三份状态的内存压力，实测 +34% 而不是理论上的 +12%。

**结论（写进结论区）**：在这套 1B + LoRA + 单卡设置里，缩放定律的瓶颈不是数据量、不是优化器、也不是内核吞吐，而是**适配器的秩**——而且秩有明确的最优点（64）。数据轴在 11.8M token 处走到地板（0.079 余量），优化器换谁都白搭（Muon +0.229、AdEMAMix −0.007），内核侧 fp16/16F 拿到 1.20×，容量侧 r16→r64 拿到 −0.073 且不多花一秒，r128 开始反向。

## 25.8 8GB 平台的两道硬墙（实测，不是估算）

1. **MTP（`--mtp_k 2`）跑不动**。第一次在 step 160 处 CUDA OOM：`chunked_offsets` 为第二路 CE 要再分 1000 MiB。把 `STPP_LOGIT_CHUNK` 从 512 降到 256 后，两次直接把**整个 WSL VM 打死**（`Wsl/Service/ERROR_NETNAME_DELETED`）——不是普通 CUDA OOM，是 guest 内存被挤爆、WSL 服务重启。结论：MTP 在这台机器上不是"调小 chunk 就能跑"，它需要第二路 CE 的完整 logits 图；要跑得换原生 Linux，或 bs=1 + 梯度累积（那就不再是同口径对比）。
2. **r64 + fp16 不能在 WDDM 上叠加**。两次尝试都在加载阶段 OOM：只差 32 MiB，而报错同时写着"4.69 GiB free"——WDDM 的单进程提交上限，不是真实显存不够。所以"容量赢家 + 速度赢家"要叠加，必须换原生 Linux（无 WDDM 上限）。
3. 附带教训：`schtasks /run` 叠加两次会让两个进程抢显存并同时被杀；开跑前先确认没有残留实例，否则日志会莫名停在 weight loading。

## 26 秩定律的实测判决：r\* = 64 与数据量无关（A 轴关档）

### 26.1 三臂实测（8.85M 语料 / 3840 步 / seed 82 / bs4 / block512 / compile）

| 臂 | 可训参数 | ppl | eval CE | 末段 train ntp | 训练墙钟 | s/步 |
|---|---|---|---|---|---|---|
| r64@3840 | 45.09M | **3.866** | 1.3522 | 1.8208 | 2788 s | 0.726 |
| r128@3840 | 90.18M | 3.898 | 1.3604 | **1.8024** | 3184 s | 0.829 |
| r64+norm@3840 | 45.16M（+0.068M） | 3.867 | 1.3524 | 1.8209 | 2338 s | 0.609 |
| *(对照) r16@3840* | 11.27M | 3.891 | — | — | 2374 s | 0.618 |

### 26.2 判决一：r128 输，而且"越喂越输"

- 固定 1920 步：r64 3.931 vs r128 3.948 → **+0.017**
- 固定 3840 步：r64 3.866 vs r128 3.898 → **+0.032**
- 且 r128 的 **train ntp 更低**（1.8024 < 1.8208）、**eval CE 更高**（1.3604 > 1.3522）——这是纯粹的过拟合签名，不是"训不动"。

差距随数据单调扩大（每翻一倍 +0.015，$\varepsilon\propto N^{0.91}$），与推导里用的 $c\,r/N$（随数据**缩小**）符号相反。所以按 $c\,r/N$ 推出的 $r^*(N)\propto N^{0.434}$（预测 3840 步时 $r^*=145$、r128 应赢）**被实测否证**。

正确的表述是：$r^*$ **不是 N 的函数**。在这套 1B + 三域混合上，$r^*=64$ 由**域偏移的内在秩**决定；超过它的秩不再是"更多容量"，而是"更多可以拟合噪声的方向"，且数据越多这些方向被拟合得越充分。

修正后的曲面（秩项封顶、超额项随数据增长）：

$$L(N,r)=L_\infty + A N^{-\alpha} + B\min(r,64)^{-\beta} + c\,(r-64)_+ N^{\delta},\quad \alpha\approx1.1,\ \beta=0.768,\ \delta\approx0.9$$

### 26.3 判决二：解冻 RMSNorm 是零收益

`--train_norms` 解冻 0.068M 个 1-D 参数，ppl **3.867 vs 3.866**（差 0.001，远小于 0.013 的 seed 噪声底）。

原先的推导（"逐通道缩放需要 d 个自由度，rank-r 的 ΔW 只覆盖 r 个方向，所以 norm 权重是免费容量"）在**表达力**上成立，在**优化**上不成立：RMSNorm 的缩放改变下一层输入的尺度，而下游权重可等价吸收该尺度（$W\cdot\mathrm{diag}(s)$ 的行缩放近似可被 W 抵消）。适配器缺的不是尺度自由度，是方向。

### 26.4 判决三：墙钟被主机内存污染了 19%

同样 r64 配置，arm1 **0.726 s/步**、arm3 **0.609 s/步**（−19%）。差别只在主机侧：`.wslconfig` 降到 6GB 后主机只剩 2.5GB 空闲，guest 在 4GB swap 上换页。**wall-clock 在这台 15.4GB 主机上不是常数**，跨臂比较必须同时记录 host free RAM，否则会出现 20% 的假差异（ppl 不受影响）。

### 26.5 平台归因修正（覆盖 §25.8 第 1 条）

"MTP 打死 WSL VM"的真因既不是 chunk、也不是显存：

| 探测 | 结果 |
|---|---|
| `wsl -d docker-desktop` | 正常启动 → VM 服务与 Hyper-V 都好 |
| vhdx 头 / 独占打开 | `vhdxfile`，未被锁 → vhdx 完好 |
| `wsl --export` | tar 正常增长 → ext4 可读 |
| `swap=0` 启动 | 仍 `E_UNEXPECTED` → 不是交换文件 |
| **`memory=10GB → 4GB`** | **立刻启动** → 根因是**主机物理内存** |

主机 15.4GB、`.wslconfig memory=10GB`：建 VM 时按配置量声索内存，宿主给不出就 `CreateInstance/E_UNEXPECTED`；MTP 多一路 CE 使 guest 峰值再涨，服务被回收（`ERROR_NETNAME_DELETED`）。当前稳定配置：`memory=6GB`、`swap=4GB`（`swapFile` 键在 WSL 3.0.5 无效）。另：E: 仅剩 0.08GB，`ext4.vhdx` 77GB，属独立隐患。

### 26.6 域差距与秩无关 → 配比是唯一还没动的杠杆

三臂的 per-domain ppl 几乎不动：code 5.32–5.40、chat 4.89–4.99、zh 2.39–2.42。**域间 2.2× 的难度差不是容量问题，是配比问题**：1:1:1 让 zh 占了过多份额，而 zh 的 loss 早已接近地板。

按 $w_d\propto(L_d-L_d^{\infty})$（地板估 4.2/3.9/1.9）得 $\approx(0.42,0.38,0.19)$，即 **4:4:2**。预计 0.02–0.04，不动显存。

### 26.7 本轮结论（替换 §25.4 的 A 轴）

- A 轴（容量/秩）**关档**：$r^*=64$，与 N 无关；r128 在全区间输，且差距随数据扩大。
- 新的最优点：**r64 @ 3840 步 / 7.86M token = 3.866**（当前最好），相对旧基线 4.004 是 **−0.138**。
- 未动的只剩两支：配比（4:4:2，预测 0.02–0.04）与内核侧反传 16F（预测 0.547→0.483 s/步）。
- 方法学教训：**先钉死参数可辨识性再拟合**——4 参数曲面在 7 个点上会把 β 拉到网格边界（0.2），必须用"同 N 的秩扫描"钉死 β、再由大 r 的偏差钉死 c。

## 27 配比轴：4:4:2 是负结果——三个域之间不迁移

### 27.1 实测（同为 r64 / 3840 步 / seed 82，唯一变量是域权重）

| 配比 | ppl | eval CE | code | chat | zh |
|---|---|---|---|---|---|
| **1:1:1（基线）** | **3.866** | 1.3522 | 5.321 | 4.885 | 2.419 |
| 4:4:2（zh 减半） | 3.912 | 1.3642 | 5.336 | 4.859 | 2.539 |
| 差 | **+0.046** | +0.0120 | +0.015 | **−0.026** | **+0.120** |

索引：`scripts/make_mix_index.py --weights 4:4:2` → 14398 块（code/chat 全取、zh 取 50%），7.37M token，1.07 epoch。

### 27.2 我推的 $w_d\propto(L_d-L_d^\infty)$ 也错了，错在"可迁移"这个前提

那条推导隐含假设"三域共享一个容量池、token 可以在域间搬运"。实测把这个前提打掉了：

- 把 zh 的 token 减半，**zh 自己的 ppl 从 2.419 涨到 2.539（+0.120）**；
- 而多喂的 code/chat 只换回 **+0.015 / −0.026**；
- 评测集是 1:1:1 均衡的，zh 的损失仍占均值 1/3，于是净亏 **+0.046**。

正确的描述是**每域独立饱和**：$L_d=L_d^{\infty}+k_d/(w_dN)$，而 $k_d$ 只对本域生效。均衡评测下的最优权重由 $\partial L_d/\partial w_d=-k_d/(w_d^2N)$ 平衡决定，不是由 excess 的线性外推决定；当各域 $k_d$ 量级接近时，最优就是**等权**——也就是基线。zh 的绝对 ppl 低（2.42），但它的 $k_{zh}$ 并不小，减半的代价远超直觉。

### 27.3 结论（比"配比不重要"更强的一条）

配比轴关档：**1:1:1 ≈ 最优**。三域在 1B / 8.8M token 这个 regime 下**互不迁移**——这是"适配器学到的是域内特化，不是可复用的语言能力"的直接证据，也解释了为什么所有"多喂难域"的直觉在这台机器上都不成立。

### 27.4 至此，全部质量轴的状态

| 轴 | 最优 | 结论 |
|---|---|---|
| 数据 | 11.8M token | 地板 3.85（r64），再翻 4 倍只买 0.015 |
| 容量/秩 | **r\*=64（与 N 无关）** | r128 全区间输，且越喂越输 |
| 优化器 | AdamW | Muon +0.229、AdEMAMix −0.007 |
| 目标函数 | — | MTP 平台受限，未取得数值 |
| 配比 | 1:1:1 | 4:4:2 = +0.046（负） |
| **当前最好** | **3.866** | 剩余质量空间 ≈ **0.01** |

**唯一还成立的方向是内核（时间，不是 ppl）**：反传 16F（GEMM 占比 1.372 → fp32 残量 $x\approx0.49$ 就在 `bgemm`），预测步时 0.547→0.483 s。**（已在 §28 实测证否：两种精度用的是同一族 fp32 累加 cutlass 核，fp16 的 GEMM 反而慢 8%。）**

### 27.5 附：这一臂的墙钟不可用

4818 s（1.25 s/步）对 2338 s（0.61 s/步），同样 r64 配置差 2 倍；步时序列在 0.95→2.5 s 之间无规律跳动，host free RAM 当时 6.9GB、guest 无换页（swap 仅用 2MB）。指向 F: 盘的随机读竞争，而非内存。**在这台机器上，wall-clock 只能在"同一时段、同一 host 负载"内比较**。

## 28. 内核轴收尾：精度不是余量，重算是墙

上一节留给内核的唯一方向是"反传 16F：把 GEMM 里的 fp32 累加残量换成 16F"。**两个 profile 把它证否了。**

### 28.1 判决表（r64 / bs4 / block512 / compile / 同 seed 82 / 同 8.85M 语料，5 步窗口）

| 量 | bf16 | fp16 | 比 |
|---|---|---|---|
| 每步 CUDA 总时 | 601.9 ms | 561.7 ms | **1.07×** |
| 其中 GEMM | 326.7 ms | 354.1 ms | **0.92×（更慢）** |
| 其中非 GEMM | 275.2 ms | 207.6 ms | 1.33× |

核名逐行对应，只是前缀不同：`ampere_bf16_s1688gemm_bf16_128x128_ldg8_f2f` ↔ `ampere_fp16_s1688gemm_fp16_...`。**两张表里都没有独立的 fp32 累加核**（没有 `sgemm`/`_fp32_` 行），说明 cuBLAS 在两种精度下都选了 fp32 累加的 cutlass 核 —— 累加精度不是 dtype 能改的开关，而是这套 kernel 的固有配置。

推论三条：

1. **"GEMM 里还有 ≈49% 的 fp32 残量"不成立。** 该推导假设 fp16 会切到 fp16 累加核、省一半数据搬运；实测 fp16 甚至更慢 8%（16816 序列在 sm_89 上 tile 更保守）。
2. **真正做到加速的是非 GEMM 的带宽**：275→208 ms，1.33×，来自 elementwise/softmax 在 fp16 下少一半读写。这才是 r16 上 1.20× 的可能来源 —— **不是 GEMM 提速**。r16 那 1.20×（1262→1051 s）在 r64 上不再复现（只有 1.07×），其中还混着 CPU/数据侧开销，标记为**未完全解释**。
3. 于是"1.372 → 0.547 s"的外推整条作废：0.547 s 本来就是 fp16 实测墙钟，0.483 s 是它对 fp32 残量的二次分配，分配对象不存在。

### 28.2 去掉梯度重算：能跑，但等于不能跑

`--no-grad_ckpt`（省掉每步一次完整前向的重算）在纸上能省 ~25% 步时。60 步探针（r64，其余同 §28.1）：

| | 有 grad_ckpt | 无 grad_ckpt |
|---|---|---|
| 显存（nvidia-smi） | 7860 / 8188 MiB | **7588–7636 / 8188 MiB（99%）** |
| 步时 | 0.726 s | **8.35 s（11.5×）** |

显存没报 OOM，但也没真装下：WDDM 在 99% 占用时把超出的激活静默分页到系统内存，每步都在跨 PCIe 搬激活。**8GB 上梯度重算是硬约束，不是可选项**；"省一次前向"这条只在 ≥12GB 的卡上存在。

### 28.3 内核轴终值

| 项 | ms/步 | 说明 |
|---|---|---|
| GEMM | 326.7 | 13.0 TFLOP → **39.8 TFLOPS = 实测峰值 48.5 的 82%** |
| 非 GEMM | 275.2 | inductor 融合 elementwise 78.2 / fmha 121.2 / softmax 28.1 / reduce 25–42 / 其余 |
| 合计 CUDA | 601.9 | 墙钟 726 ms（CPU 侧 124 ms 是采样+索引，已压过） |

内核侧只剩两条路：换 dtype（1.07×，且 **r64+fp16 在模型加载阶段就 OOM**，不可组合）、换硬件。**六条轴至此全部关档。**

### 28.4 六轴终表

| 轴 | 结论 | 剩余余量 |
|---|---|---|
| 数据 | 8.85M token，1.11 指数，地板 3.85 | ≈0.015 |
| 容量 | r*=64 与 N 无关 | ≈0.01 |
| 优化器 | AdamW | 0 |
| 目标 | MTP 撞 8GB/宿主内存 | 未取得数值 |
| 配比 | 1:1:1 | 0 |
| 内核 | GEMM 82% 峰值，非 GEMM 已被 fp16 榨过 | 1.07×（不可组合） |

**最终配方（唯一可交付的一条）：r64 / α=128 / bf16 / grad_ckpt / bs4 / block512 / compile / AdamW / 3840 步 = ppl 3.866，0.726 s/步。**
相对起点（Windows 1.37 s/步、4.004）是 **1.89× 墙钟 + −0.138 ppl**。
## 29. 重开内核轴：FP8 在 sm_89 是通的，但接不进这张 8GB 卡

§28 判定"内核轴关闭"的前提是"FP8 不可用"——那个结论来自 `cublasGemmEx` 老接口的 UNSUPPORTED。**这一节把它推翻了：`torch._scaled_mm`（cuBLASLt 路径）在 sm_89 上能跑 FP8，而且是把 bf16 翻一倍。**

### 29.1 裸 GEMM 实测（我们的四个真实 shape）

| shape | bf16 | FP8 张量级缩放 | 比 |
|---|---|---|---|
| 2048×2048×8192（gate/up） | 40.3 TFLOPS | **87.9** | 2.18× |
| 2048×8192×2048（down） | 41.7 | **84.0** | 2.01× |
| 2048×2048×128256（lm_head） | 45.6 | **86.8** | 1.90× |
| 512×2048×128256（logits 切块） | 45.4 | **85.0** | 1.87× |

缩放方案的判决是硬的：**只有张量级（每操作数一个标量）能到 88 TFLOPS**；逐行/逐列缩放在同一 shape 上只有 34.6 TFLOPS，比 bf16 还慢（cuBLASLt 把它打回慢路径）。激活量化的开销 0.10 ms，可忽略。

### 29.2 接进训练器：两次都更慢

| 版本 | 做法 | 步时 | vs bf16 0.726 |
|---|---|---|---|
| v1 | 每步现量化权重（省显存） | **3.05 s** | 4.2× 慢 |
| v2 | 权重预存两份 FP8（(N,K)+(K,N)），内存与 bf16 持平 | **2.65 s** | 3.6× 慢 |

v2 的精度反而是好消息：step 0 的 `ntp` = **1.7819**，bf16 是 1.7862，**差 −0.004（0.2%）**。也就是说 e4m3 前向+反传对损失几乎无损 —— 我先前用合成分布算出的 3.75% 误差是虚高的。

慢的原因不是 GEMM，是它周围的一切：
- 每个 linear 每步要做一次全张量 `amax` → 标量（112 个 linear）；
- `_scaled_mm` 要求 B 列主序，编译图里为满足步长约束会插入布局拷贝；
- 梯度重算让前向做两遍，上述开销也付两遍。

粗算：GEMM 省下的 326.7→~175 ms 是 152 ms，而量化+拷贝在 112 个 linear × 2 遍上的实测代价是 ~1900 ms。**方向对，工程错。**

### 29.3 顺带查出的两个真问题

1. **head 链的单步成本 61.3 ms**（profile 里那个 69 ms 核就是它）：前向 23.5 + CE 与 dgrad 37.8。dgrad 吃到 fp32 的 CE 梯度，所以比 bf16 GEMM 慢一倍。CE 梯度改 bf16 可省 ~14 ms/步。
2. **`STPP_LOGIT_CHUNK=64` 是陷阱**：同一 shape，chunk=64 是 **151.9 ms**，chunk=512（单块）是 **61.3 ms**，差 2.5×。分块越小越快是错的，只有"整块一次"才是快路径；分块的价值只在省显存。

### 29.4 于是内核轴的结论要改写

不是"没有余量"，而是"余量存在但必须自己写核"：

| 路线 | 预期 | 代价 |
|---|---|---|
| 自写 FP8 GEMM（mma.sync e4m3，量化融进 kernel） | GEMM 326.7 → ~180 ms，步时 0.726 → **~0.55 s（1.3×）** | WSL 里 nvcc 有，要自己写 m16n8k32 的 sm_89 核；这是唯一 >10% 的余量 |
| CE 梯度降 bf16 | −14 ms/步（2%） | 改两行 |
| block 256 / bs 8（token 数不变） | attention 的 L² 项减半，fmha 121→~60 ms（**~10%**） | ppl 需重测，训练 block 与 eval block 不一致 |

**注意**：FP8 若走自写核，显存反而友好（base 权重 2.48 GB → 1.24 GB），甚至能把省下的 1.2GB 还给激活。
